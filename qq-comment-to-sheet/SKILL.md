# QQ 评论排单转表格

将带有时间戳、用户名和购买指令的评论记录转换为“商品行 × 可配置槽位”的 Markdown 排单表。

## 生成前必须确认表参数

在分配任何槽位前，先确定并展示：

1. `products`：商品简称及最终行顺序。
2. 商品行数：等于 `products` 的长度。
3. `slot_count`：每个商品的库存槽位数，必须是大于 0 的整数。

优先从用户资料推断：

- 表格中的商品行可推断商品集合和顺序。
- 表格列名、截图列数、明确的库存数量可推断 `slot_count`。
- 只有“第1配”至“第N配”等列时，N 可作为候选槽位数。
- 用户提供的库存、余量或明确数字优先于画面列数。

默认值仅在资料无法确定或用户选择默认时使用：

- `products`：千、曜、梨、丸、露、善、黛、鞠、南。
- 商品行数：9。
- `slot_count`：9。

**无论参数是从资料推断出来还是使用默认值，都必须向用户说明依据并询问确认。** 不得在用户确认前生成排单表。若用户在同一条消息中已经明确给出并确认了这些参数，可直接使用该确认结果。

确认示例：

> 我从资料中识别到 4 个商品、每商品 6 个槽位；或若资料不足，将采用默认的 9 个商品、每商品 9 个槽位。是否按该配置生成？

## 输入

接受以下任一输入：

- 文本记录，每条包含时间戳、用户名和评论内容。
- 评论截图；先逐条读取时间戳、用户名和评论内容。
- 用户提供的自定义商品顺序或映射。

如果时间戳、用户名或购买指令无法辨认，停止分配并指出缺失的记录。不要猜测或补造数据。

## 商品映射

默认映射：

| 全称 | 简称 |
| --- | --- |
| 千歌 | 千 |
| 曜 | 曜 |
| 梨子 | 梨 |
| 花丸 | 丸 |
| 露比 | 露 |
| 善子 | 善 |
| 黛雅 | 黛 |
| 鞠莉 | 鞠 |
| 果南 | 南 |

用户提供的自定义映射优先于默认映射。按别名长度从长到短替换，避免短别名覆盖长别名。若同一别名映射到多个简称，停止并请求用户确认。

最终商品行及顺序以用户确认的 `products` 为准。未在 `products` 中的商品不得擅自新增。

## 解析规则

1. 先标准化商品名，再解析数量和优先级。
2. 将“两个简称加一个数量词”拆成两个请求。例如：
   - `善梨凹` → `善凹`、`梨凹`
   - `千曜2` → `千2`、`曜2`
3. 支持以下请求形式：
   - `商品n`：占用该商品连续 n 个槽位，n 必须是大于 0 的整数。
   - `商品凹`：占用处理到该请求时该商品的全部剩余槽位。
   - `提商品n` 或 `提商品凹`：与上述规则相同，但属于优先请求。
4. 一条评论包含多个请求时，每个请求独立分配。例如 `千1 (提善1)` 表示一个普通“千1”请求和一个优先“善1”请求。
5. 忽略 `tt`、纯标点、纯空白和明确的非下单闲聊。看起来像下单但无法解析的内容必须停止并请求确认。
6. 同一用户可占用多个槽位。超过已确认 `slot_count` 的部分不分配。

## 用户名

用户名单独取评论记录的用户名列。若文本行把用户名与评论写在一起，按第一个空格切分，只保留第一个子串作为用户名。

示例：`AB 黛凹` 中，用户名是 `AB`，请求是 `黛凹`。

## 分配顺序

1. 先分配所有带“提”的请求。
2. 再分配其余请求。
3. 两个分组内部都按时间戳从早到晚排序。
4. 时间戳相同时，保留输入记录中的先后顺序；若截图的纵向顺序无法判断，停止并请求确认。

逐条顺序分配。“凹”只拿该请求处理时对应商品的剩余槽位，不影响其他商品。

## 输出

输出一个 Markdown 表格：

- 行头为已确认的 `products`。
- 列表头为 `1` 至已确认的 `slot_count`。
- 单元格只写用户名；空槽位留空。
- 发生超售时，在表格后追加 `超售未分配：用户名-商品×数量；...`。
- 未确认表参数或没有可分配数据时，不输出伪造表格。

具体输入与预期输出见 [worked-examples.md](references/worked-examples.md)。
